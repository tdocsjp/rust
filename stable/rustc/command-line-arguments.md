# コマンドライン引数

ここでは、`rustc` のコマンドライン引数とその動作を網羅的に紹介します。

## `-h`/`--help`: ヘルプを表示する

このフラグは `rustc` のヘルプ情報を出力します。

## `--cfg`: コンパイル環境を設定する

このフラグは、[条件付きコンパイル](/stable/reference/conditional-compilation.html)のために様々な `#[cfg]` 設定を有効・無効にできます。

値は、単一の識別子、または `=` で区切られた2つの識別子のいずれかです。

例として `--cfg 'verbose'` や `--cfg 'feature="serde"'` は、それぞれ `#[cfg(verbose)]` と `#[cfg(feature = "serde")]` に対応します。

## `--check-cfg`: 条件付きコンパイルのコンパイル時チェックを設定する

このフラグは、クレートの条件付き設定をコンパイル時にチェックすることを有効にします。具体的には、期待される cfg の名前と値の集合を設定し、_到達可能な_すべての `#[cfg]` が、期待される設定の名前と値に一致することをチェックするのに役立ちます。

これは上記の `--cfg` フラグとは異なります。`--cfg` は設定を有効化しますが、それを期待済みとはしません。これは、動かない条件やタイプミスなどを防ぐのに有用です。

詳細と解説については、この本の[条件付き設定のチェック](check-cfg.html)を参照してください。

例として `--check-cfg 'cfg(verbose)'` や `--check-cfg 'cfg(feature, values("serde"))'` は、それぞれ `#[cfg(verbose)]` と `#[cfg(feature = "serde")]` に対応します。

## `-L`: ライブラリ検索パスにディレクトリを追加する

`-L` フラグは、外部クレートやライブラリを検索するパスを追加します。

検索パスの種類は、`-L KIND=PATH` という形式で任意に指定できます。`KIND` は次のいずれかです。

* `dependency` — このディレクトリでは推移的な依存だけを検索する
* `crate` — このディレクトリではこのクレートの直接の依存だけを検索する
* `native` — このディレクトリではネイティブライブラリだけを検索する
* `framework` — このディレクトリでは macOS のフレームワークだけを検索する
* `all` — フレームワークを除くすべての種類のライブラリをこのディレクトリで検索する。`KIND` が指定されない場合のデフォルト

## `-l`: 生成したクレートをネイティブライブラリにリンクする

構文: `-l [KIND[:MODIFIERS]=]NAME[:RENAME]`

このフラグを使うと、クレートをビルドする際に特定のネイティブライブラリへのリンクを指定できます。

ライブラリの種類は `-l KIND=lib` という形式で任意に指定できます。`KIND` は次のいずれかです。

* `dylib` — ネイティブな動的ライブラリ
* `static` — ネイティブな静的ライブラリ（`.a` アーカイブなど）
* `framework` — macOS のフレームワーク

種類を指定した場合、リンクの修飾子 (modifier) を付加できます。修飾子はカンマ区切りの文字列で指定し、各修飾子の前に `+` または `-` を付けて、その修飾子を有効にするか無効にするかを示します。1つの `link` 属性に複数の `modifiers` 引数を指定すること、あるいは同じ `modifiers` 引数の中に同一の修飾子を複数指定することは、現在サポートされていません。
例: `-l static:+whole-archive=mylib`

ライブラリの種類と修飾子は、[`#[link]` 属性](/stable/reference/items/external-blocks.html#the-link-attribute)でも指定できます。種類が `link` 属性でもコマンドラインでも指定されない場合、静的実行可能ファイルをビルドする場合を除き、デフォルトで動的ライブラリをリンクします。コマンドラインで種類が指定された場合、それが `link` 属性で指定された種類を上書きします。

`link` 属性で使われる名前は、`-l ATTR_NAME:LINK_NAME` という形式で上書きできます。`ATTR_NAME` は `link` 属性内の名前で、`LINK_NAME` は実際にリンクされるライブラリの名前です。

### リンク修飾子: `whole-archive`

この修飾子は `static` のリンク種別とのみ互換性があります。他の種別で使うとコンパイルエラーになります。

`+whole-archive` は、オブジェクトファイルを1つも捨てずに、静的ライブラリをアーカイブ全体としてリンクすることを意味します。

この修飾子は、`ld` 系のリンカでは `--whole-archive` に、`link.exe` では `/WHOLEARCHIVE` に、`ld64` では `-force_load` に変換されます。サポートしていないリンカに対しては何もしません。

この修飾子のデフォルトは `-whole-archive` です。

### リンク修飾子: `bundle`

この修飾子は `static` のリンク種別とのみ互換性があります。他の種別で使うとコンパイルエラーになります。

rlib または staticlib をビルドする場合、`+bundle` は、ネイティブな静的ライブラリが rlib または staticlib のアーカイブにパックされ、最終的なバイナリをリンクする際にそこから取り出されることを意味します。

rlib をビルドする場合、`-bundle` は、ネイティブな静的ライブラリがその rlib の依存として「名前によって」登録され、そこからのオブジェクトファイルは最終的なバイナリをリンクする際にのみ含まれる（その名前でのファイル検索も最終リンク時に行われる）ことを意味します。
staticlib をビルドする場合、`-bundle` は、ネイティブな静的ライブラリが単純にアーカイブに含まれず、より上位のビルドシステムが最終的なバイナリのリンク時にそれを追加する必要があることを意味します。

この修飾子は、実行可能ファイルや動的ライブラリなど、他のターゲットをビルドする際には効果がありません。

この修飾子のデフォルトは `+bundle` です。

### リンク修飾子: `verbatim`

この修飾子はすべてのリンク種別と互換性があります。

`+verbatim` は、rustc 自身がライブラリ名にターゲット固有の接頭辞・接尾辞（`lib` や `.a` など）を追加せず、リンカにも同じことを求めるよう最善を尽くすことを意味します。

GNU 拡張をサポートする `ld` 系のリンカに対しては、rustc はライブラリを渡す際に `-l:filename` という構文（コロンに注意）を使うため、リンカはそれに接頭辞・接尾辞を追加しません。詳細は ld のドキュメントの [`-l namespec`](https://sourceware.org/binutils/docs/ld/Options.html) を参照してください。
verbatim 修飾子をサポートしないリンカ（`link.exe` や `ld64` など）では、ライブラリ名はそのまま渡されます。そのため、このオプションが最も信頼できるクロスプラットフォームな利用場面は、リンカが介在しない場合、たとえばネイティブライブラリを rlib にバンドルする場合です。

`-verbatim` は、rustc がライブラリ名にターゲット固有の接頭辞・接尾辞をリンカに渡す前に追加するか、リンカが暗黙にそれを追加することを妨げない、ということを意味します。
特に `raw-dylib` 種別の場合、Windows ではライブラリ名に `.dll` が追加されます。

この修飾子のデフォルトは `-verbatim` です。

注意: `+verbatim` と `-l:filename` 構文を使っても、`ld` 系のリンカは通常、ライブラリへの絶対パスの指定をサポートしません。通常、そのようなパスは `-l` のようなオプションを使わずに入力ファイルとして渡す必要があります（例: `ld /my/absolute/path`）。
stable な `rustc` からこれを行うには `-Clink-arg=/my/absolute/path` を使えます。

## `--crate-type`: コンパイラが出力するクレートの種類の一覧

これは `rustc` に、どのクレート種別をビルドするかを指示します。このフラグはカンマ区切りの値のリストを受け取り、複数回指定することもできます。有効なクレート種別は次の通りです。

* `lib` — コンパイラが好むライブラリ種別を生成する。現在のデフォルトは `rlib`
* `rlib` — Rust の静的ライブラリ
* `staticlib` — ネイティブな静的ライブラリ
* `dylib` — Rust の動的ライブラリ
* `cdylib` — ネイティブな動的ライブラリ
* `bin` — 実行可能なプログラム
* `proc-macro` — コンパイラがロードできる、手続き的マクロライブラリに適した形式を生成する

クレート種別は [`crate_type` 属性](/stable/reference/linkage.html)でも指定できます。`--crate-type` コマンドライン値は `crate_type` 属性を上書きします。

詳しくはリファレンスの[リンケージの章](/stable/reference/linkage.html)を参照してください。

## `--crate-name`: ビルドするクレートの名前を指定する

これは `rustc` にクレートの名前を伝えます。

## `--edition`: 使用するエディションを指定する

このフラグは `2015`、`2018`、`2021`、`2024` のいずれかの値を取ります。デフォルトは `2015` です。エディションについての詳細は[エディションガイド](/stable/edition-guide/introduction.html)を参照してください。

## `--emit`: 生成する出力ファイルの種類を指定する

このフラグは、コンパイラが生成する出力ファイルの種類を制御します。カンマ区切りの値のリストを受け取り、複数回指定することもできます。有効な emit の種類は次の通りです。

* `asm` — クレートのアセンブリコードを含むファイルを生成する。デフォルトの出力ファイル名は `CRATE_NAME.s`
* `dep-info` — クレートを生成するために読み込まれたすべてのソースファイルを示す、Makefile 構文のファイルを生成する。デフォルトの出力ファイル名は `CRATE_NAME.d`
* `link` — `--crate-type` で指定されたクレートを生成する。デフォルトの出力ファイル名はクレート種別とプラットフォームに依存する。`--emit` が指定されない場合のデフォルト
* `llvm-bc` — [LLVM bitcode](https://llvm.org/docs/BitCodeFormat.html) を含むバイナリファイルを生成する。デフォルトの出力ファイル名は `CRATE_NAME.bc`
* `llvm-ir` — [LLVM IR](https://llvm.org/docs/LangRef.html) を含むファイルを生成する。デフォルトの出力ファイル名は `CRATE_NAME.ll`
* `metadata` — クレートに関するメタデータを含むファイルを生成する。デフォルトの出力ファイル名は `libCRATE_NAME.rmeta`
* `mir` — rustc の中間レベル中間表現を含むファイルを生成する。デフォルトの出力ファイル名は `CRATE_NAME.mir`
* `obj` — ネイティブなオブジェクトファイルを生成する。デフォルトの出力ファイル名は `CRATE_NAME.o`

出力ファイル名は [`-o` フラグ](#-o-出力ファイル名)で設定できます。[`-C extra-filename` フラグ](codegen-options/index.html#extra-filename)でファイル名に接尾辞を追加することもできます。

出力ファイルは、[`--out-dir` フラグ](#--out-dir-出力を書き込むディレクトリ)を使わない限り、現在のディレクトリに書き込まれます。

### 個々の emit 種別ごとのカスタムパス

各 emit 種別の後に `=` を付けることで、その種類の出力にのみ適用される明示的な出力パスを任意で指定できます。たとえば:

* `--emit=link,dep-info=/path/to/dep-info.d`
  * クレート自体を通常どおり出力し、依存情報も指定したパスへ出力する
* `--emit=llvm-ir=-,mir`
  * MIR はデフォルトのファイル名（クレート名に基づく）で出力し、LLVM IR は標準出力へ出力する

### 標準出力への出力

`--emit` または [`-o`](#-o-出力ファイル名) を使う際、パスとして `-` を指定することで、出力を標準出力へ送ることができます（例: `-o -`）。

バイナリの出力種別は、標準出力が tty でない場合にのみ標準出力へ書き込めます。テキストの出力種別（`asm`、`dep-info`、`llvm-ir`、`mir`）は、tty であるかどうかに関わらず標準出力へ書き込めます。

標準出力へ書き込めるのは1種類の出力だけです。複数の種類を同時に標準出力へ書き込もうとするとエラーになります。

## `--print`: コンパイラの情報を出力する

このフラグで[print オプション](command-line-arguments/print-options.html)を設定できます。

## `-g`: デバッグ情報を含める

[`-C debuginfo=2`](codegen-options/index.html#debuginfo) の別名です。

## `-O`: コードを最適化する

[`-C opt-level=3`](codegen-options/index.html#opt-level) の別名です。

## `-o`: 出力ファイル名

このフラグは出力ファイル名を制御します。

## `--out-dir`: 出力を書き込むディレクトリ

出力されるクレートはこのディレクトリに書き込まれます。[`-o` フラグ](#-o-出力ファイル名)が使われている場合、このフラグは無視されます。

## `--explain`: エラーメッセージの詳細な説明を提供する

`rustc` の各エラーにはエラーコードが付いています。これは、与えられたエラーについての、より長い説明を出力します。

## `--test`: テストハーネスをビルドする

このクレートをコンパイルする際、`rustc` は `main` 関数を無視し、代わりにテストハーネスを生成します。テストについての詳細は[テストの章](tests/index.html)を参照してください。

## `--target`: ビルドするターゲットタプルを選ぶ

これは、どの[ターゲット](targets/index.html)を生成するかを制御します。

## `-W`: lint の警告を設定する

このフラグで、どの lint を[警告レベル](lints/levels.html#warn)にするかを設定できます。

_注意:_ これらの lint レベル引数は順序が考慮されます。詳しくは[コンパイラフラグによる lint レベル](lints/levels.html#via-compiler-flag)を参照してください。

## `--force-warn`: lint を強制的に警告にする

このフラグは、指定した lint を[強制的な警告レベル](lints/levels.html#force-warn)に設定します。このレベルは、[lint の上限](lints/levels.html#capping-lints)を無視してでも上書きできません。

## `-A`: lint を許可する

このフラグで、どの lint を[許可レベル](lints/levels.html#allow)にするかを設定できます。

_注意:_ これらの lint レベル引数は順序が考慮されます。詳しくは[コンパイラフラグによる lint レベル](lints/levels.html#via-compiler-flag)を参照してください。

## `-D`: lint を禁止する

このフラグで、どの lint を[禁止レベル](lints/levels.html#deny)にするかを設定できます。

_注意:_ これらの lint レベル引数は順序が考慮されます。詳しくは[コンパイラフラグによる lint レベル](lints/levels.html#via-compiler-flag)を参照してください。

## `-F`: lint を forbid にする

このフラグで、どの lint を[forbid レベル](lints/levels.html#forbid)にするかを設定できます。

_注意:_ これらの lint レベル引数は順序が考慮されます。詳しくは[コンパイラフラグによる lint レベル](lints/levels.html#via-compiler-flag)を参照してください。

## `-Z`: unstable オプションを設定する

このフラグで rustc の unstable オプションを設定できます。複数のオプションを設定するには、-Z フラグを複数回使えます。例: `rustc -Z verbose-internals -Z time-passes`。-Z によるオプション指定は nightly でのみ利用できます。利用可能なすべてのオプションを見るには `rustc -Z help` を実行するか、[The Unstable Book](/stable/unstable-book/) を参照してください。

## `--cap-lints`: 最も厳しい lint レベルを設定する

このフラグで lint を「キャップ (cap)」できます。詳しくは[こちら](lints/levels.html#capping-lints)を参照してください。

## `-C`/`--codegen`: コード生成オプション

このフラグで[コード生成オプション](codegen-options/index.html)を設定できます。

## `-V`/`--version`: バージョンを出力する

このフラグは `rustc` のバージョンを出力します。

## `-v`/`--verbose`: 詳細な出力を使う

このフラグは、他のフラグと組み合わせると、それらに追加の出力をさせます。

## `--extern`: 外部ライブラリの場所を指定する

このフラグで、直接依存する外部クレートの名前と場所を渡せます。間接的な依存（依存の依存）は [`-L` フラグ](#-l-ライブラリ検索パスにディレクトリを追加する)を使って見つけられます。指定したクレート名は、ルートモジュール内で `extern crate` を指定するのと同様に、[extern prelude](/stable/reference/names/preludes.html#extern-prelude) に追加されます。指定するクレート名は、そのライブラリがビルドされた際の名前と一致する必要はありません。

`--extern` の指定には `extern crate` との振る舞いの違いが1つあります。`--extern` は単にそのクレートをリンクの_候補_にするだけで、実際に使われない限りリンクしません。コードから積極的に使っていなくても、クレートが確実にリンクされるようにしたい稀な場合があります。たとえば、グローバルアロケータを変更する場合や、他のプログラミング言語が使う `#[no_mangle]` シンボルを含む場合です。そのような場合には `extern crate` を使う必要があります。

このフラグは複数回指定できます。このフラグは次のいずれかの形式の引数を取ります。

* `CRATENAME=PATH` — 指定したクレートが指定したパスにあることを示す
* `CRATENAME` — 指定したクレートが、sysroot や `-L` フラグなどの検索パスの中にあることを示す

同じクレート名を、異なるクレート種別に対して複数回指定できます。`rlib` と `dylib` の両方が見つかった場合、どちらをリンクに使うかは内部のアルゴリズムで決まります。[`-C prefer-dynamic` フラグ](codegen-options/index.html#prefer-dynamic)で、どちらが使われるかに影響を与えられます。

同じクレート名がパス付きとパスなしの両方で指定された場合、パス付きの方が使われ、パスなしのフラグは効果を持ちません。

## `--sysroot`: システムルートを上書きする

「sysroot」は、`rustc` が Rust ディストリビューションに付属するクレートを探す場所です。このフラグでこれを上書きできます。

## `--error-format`: エラーの出力方法を制御する

このフラグでメッセージの形式を制御できます。メッセージは標準エラー出力に出力されます。有効なオプションは次の通りです。

* `human` — 人間が読める出力。デフォルト
* `json` — 構造化された JSON 出力。詳細は[JSON の章](json.html)を参照
* `short` — 短い、1行のメッセージ

## `--color`: 出力の色付けを設定する

このフラグで出力の色設定を制御できます。有効なオプションは次の通りです。

* `auto` — 出力が tty へ向かう場合に色を使う。デフォルト
* `always` — 常に色を使う
* `never` — 出力を色付けしない

## `--diagnostic-width`: 診断メッセージの端末幅を指定する

このフラグは、端末の幅を文字数で指定する数値を取ります。診断メッセージの整形は、画面にうまく収まるよう、この幅を考慮します。

## `--remap-path-prefix`: 出力内のソースパスを置き換える

コンパイラの診断メッセージ、デバッグ情報、マクロ展開など、すべての出力でソースパスの接頭辞を置き換えます。`FROM=TO` という形式の値を取り、`FROM` に等しいパス接頭辞が値 `TO` に書き換えられます。このフラグは複数回指定できます。

詳細と解説はこの本の[ソースパスの置き換え](remap-source-paths.html)の章を参照してください。

## `--remap-path-scope`: 出力内のソースパスを置き換える

`--remap-path-prefix` によって置き換えるべきパスの範囲を定義します。

詳細と解説はこの本の[ソースパスの置き換え](remap-source-paths.html)の章を参照してください。

## `--json`: コンパイラが出力する json メッセージを設定する

[`--error-format=json` オプション](#--error-format-エラーの出力方法を制御する)が rustc に渡されると、コンパイラの診断出力はすべて JSON の塊として出力されます。`--json` 引数は `--error-format=json` と組み合わせて、JSON の塊に何を含めるか、どれを出力するかを設定するために使えます。

`--error-format=json` を使うと、コンパイラは常にコンパイルエラーを JSON の塊として出力しますが、出力をカスタマイズするために `--json` フラグには次のオプションも使えます。

* `diagnostic-short` — 診断メッセージの JSON の塊で、通常のデフォルトである「human」表示の代わりに「short」表示を使うべきことを示す。つまり `--error-format=short` の出力が、デフォルトの `--error-format=human` の代わりに JSON 診断へ埋め込まれる
* `diagnostic-rendered-ansi` — デフォルトでは、JSON の塊の `rendered` フィールドには診断のプレーンテキスト表示が含まれる。このオプションは代わりに、rustc が端末出力に対して通常行っているのと同じ方法でメッセージを色付けするための、ANSI カラーコードが埋め込まれた診断を示す。これは [`fwdansi`](https://crates.io/crates/fwdansi) のようなクレートと組み合わせて Windows 上でこれらの ANSI コードをコンソールコマンドに変換したり、後で ANSI カラーを取り除きたい場合は [`strip-ansi-escapes`](https://crates.io/crates/strip-ansi-escapes) と組み合わせたりすると有用
* `artifacts` — 生成される各アーティファクトについて JSON の塊を出力するよう rustc に指示する。アーティファクトは [`--emit` CLI 引数](#--emit-生成する出力ファイルの種類を指定する)からの要求に対応し、そのアーティファクトがファイルシステム上で利用可能になるとすぐに通知が出力される
* `future-incompat` — クレートに将来コンパイルに失敗する可能性のあるコードが含まれている場合、それを報告する JSON メッセージを含める
* `timings` — 特定のコンパイルの「セクション」（フロントエンド解析、コード生成、リンクなど）が開始・終了したときに JSON メッセージを出力する

`--json` 引数を [`--color`](#--color-出力の色付けを設定する) 引数と組み合わせることは無効であり、`--json` は `--error-format=json` と組み合わせることが必須であることに注意してください。

詳細は[JSON の章](json.html)を参照してください。

## `-j`/`--jobs`、`--jobs-frontend`、`--jobs-backend`、`--jobs-linker`: 並列度を制限する

これらのフラグは、コンパイラ、またはその特定の部分が使う並列ジョブの最大数を指定します。

いずれのオプションも 0 から 255 の数値、または `sync` を受け取ります。

* `0` は利用可能な論理 CPU の数に等しい
* `sync` は `1` と同等だが、（ベンチマーク用に）同期オーバーヘッドが有効になる

`jobs` はすべてに対する共通の上限であり、より具体的な `jobs-*` オプションはそれより大きい値を指定できません。

### フロントエンドの並列性

字句解析からバックエンド IR（LLVM IR など）の生成までのコンパイル段階で使われる並列性。

* `jobs-frontend` が渡されていれば、それが上限として使われる
* そうでなく `jobs` が渡されていれば、それが上限として使われる
* そうでなければ `1` が上限として使われる（並列性は無効）。このデフォルトは変わる可能性がある

いずれの場合も、ここでの並列性は、cargo のような上位のビルドシステムから渡される jobserver によって、動的に追加で制限されることがあります。

### バックエンドの並列性

バックエンド IR をオブジェクトファイルに変換するコンパイル段階で使われる並列性。

* `jobs-backend` が渡されていれば、それが上限として使われる
* そうでなく `jobs` が渡されていれば、それが上限として使われる
* そうでなければ `32` が上限として使われるか、継承された jobserver がある場合は上限がない。このデフォルトは変わる可能性がある

いずれの場合も、ここでの並列性は、cargo のような上位のビルドシステムから渡される jobserver によって、動的に追加で制限されることがあります。

### リンカの並列性

オブジェクトファイルを最終的なバイナリへ結合する際にリンカが使う並列性。

* `jobs-linker` が渡されていれば、それが上限として使われる
* そうでなく `jobs` が渡されていれば、それが上限として使われる
* そうでなければリンカには何もオプションが渡されず、そのデフォルトの動作が使われる。このデフォルトは変わる可能性がある

注意: このオプションはベストエフォートです。リンカが並列性をサポートしていなければ有効化できず、リンカがデフォルトで並列性を使い、それを制限する方法がなければ制限できません。

現時点では LLD だけが並列性の制御をサポートしています。

## `@path`: パスからコマンドラインフラグを読み込む

コマンドラインで `@path` を指定すると、`path` を開いてそこからコマンドラインオプションを読み込みます。これらのオプションは1行に1つで、空行は空のオプションを示します。このファイルは Unix 形式・Windows 形式どちらの行末も使え、UTF-8 でエンコードされている必要があります。
