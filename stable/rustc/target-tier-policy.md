# Target Tier Policy（要約）

## 目的

Target Tier Policy は、Rust において異なるターゲットプラットフォームをサポートするための要件とプロセスを定めた文書です。Rust プロジェクトからのコミットメントと保証のレベルが増していく3つの Tier を定義し、ターゲットがこれらの Tier を追加・昇格する方法を規定します。

## Tier ごとの大まかな要件

### Tier 3（最小限の保証）

Rust は**公式のサポートを提供しません**。他の Rust の開発を妨げないことに重点が置かれます。

**主な要件:**
- 登録されたメンテナが存在すること
- 一貫した命名規則
- 法的・ライセンス上の問題や、独占的な依存がないこと
- ビルド・テストのためのドキュメント
- 他の開発者の負担にならないこと
- Tier 2/1 のターゲットを壊さないこと

### Tier 2（ビルドの保証）

Rust は、そのターゲットが**CI で確実にビルドできる**ことを保証します（テストは失敗する場合があります）。

**主な要件:**
- メンテナ以外の複数の人にとっての価値が示されていること
- 2名以上のメンテナのチーム
- クロスコンパイルやテストを含む完全なドキュメント
- core・標準ライブラリのサポート（大きな欠落がないこと）
- 健全なコード生成（安全性違反がないこと）
- テストの失敗で他の開発者に負担をかけないこと
- 他のターゲットと同程度の CI ビルド時間

**ホストツール付きの場合:** 他者にとって直接的な価値があり、合理的に利用が見込まれること。ツールも CI で確実にビルドできること。

### Tier 1（完全な保証）

Rust は、そのターゲットが**ビルドでき、すべてのテストに通る**ことを保証します。それを壊すパッチは却下されます。

**主な要件:**
- 複数の組織・プロジェクトにわたる、実質的で広範な関心
- 3名以上のメンテナのチーム
- 確実な CI ビルドと、すべてのテストの通過
- 可能な限りの完全な標準ライブラリサポート
- タイムリーなテストに耐えられる性能
- 署名済み・承認済みバイナリの絶対的な要件はない
- 必要であれば、メンテナがインフラ（ハードウェア・エミュレーション）を提供する

**ホストツール付きの場合:** ネイティブコンパイルに対する広範な実運用上の関心があること。通常、標準的なツール（rustc、cargo、clippy、rustfmt）がすべて含まれること。CI で確実にビルド・テストできること。
