# Struct Vec

```rust
pub struct Vec<T, A: Allocator = Global> { /* private fields */ }
```

`Vec<T>` と表記される、連続した可変長の配列型。「vector」の略です。

## 使用例

```rust
let mut vec = Vec::new();
vec.push(1);
vec.push(2);

assert_eq!(vec.len(), 2);
assert_eq!(vec[0], 1);

assert_eq!(vec.pop(), Some(2));
assert_eq!(vec.len(), 1);

vec[0] = 7;
assert_eq!(vec[0], 7);

vec.extend([1, 2, 3]);

for x in &vec {
    println!("{x}");
}
assert_eq!(vec, [7, 1, 2, 3]);
```

便利な初期化のために [`vec!`](/stable/std/) マクロが用意されています。

```rust
let mut vec1 = vec![1, 2, 3];
vec1.push(4);
let vec2 = Vec::from([1, 2, 3, 4]);
assert_eq!(vec1, vec2);
```

`Vec<T>` の各要素を、与えた値で初期化することもできます。これは、確保と初期化を別々のステップで行うより効率的な場合があります。特にゼロのベクタを初期化する場合などです。

```rust
let vec = vec![0; 5];
assert_eq!(vec, [0, 0, 0, 0, 0]);

// 下記は同等だが、遅くなる可能性がある:
let mut vec = Vec::with_capacity(5);
vec.resize(5, 0);
assert_eq!(vec, [0, 0, 0, 0, 0]);
```

`Vec<T>` を効率的なスタックとして使う:

```rust
let mut stack = Vec::new();

stack.push(1);
stack.push(2);
stack.push(3);

while let Some(top) = stack.pop() {
    // 3, 2, 1 の順に出力される
    println!("{top}");
}
```

## インデックスアクセス

`Vec` 型は [`Index`](/stable/std/ops/) トレイトを実装しているため、インデックスによる値へのアクセスができます。例で見るとより明確です。

```rust
let v = vec![0, 2, 4, 6];
println!("{}", v[1]); // '2' が表示される
```

ただし注意してください。`Vec` にないインデックスにアクセスしようとすると、プログラムはパニックします！ 次のようなことはできません。

```rust
let v = vec![0, 2, 4, 6];
println!("{}", v[6]); // パニックする！
```

インデックスが `Vec` の範囲内かどうかを確認したい場合は、[`get`](/stable/std/primitive.slice.html) と [`get_mut`](/stable/std/primitive.slice.html) を使ってください。

## スライス化

`Vec` は可変にできます。一方、スライスは読み取り専用のオブジェクトです。[スライス](/stable/std/primitive.slice.html)を得るには [`&`](/stable/std/primitive.reference.html) を使います。例:

```rust
fn read_slice(slice: &[usize]) {
    // ...
}

let v = vec![0, 1];
read_slice(&v);

// ... それだけです！
// こう書くこともできます:
let u: &[usize] = &v;
// あるいはこう:
let u: &[_] = &v;
```

Rust では、単に読み取りアクセスを提供したいだけの場合、ベクタそのものよりもスライスを引数として渡す方が一般的です。[`String`](/stable/std/string/) と [`&str`](/stable/std/primitive.str.html) についても同様です。

## 容量 (capacity) と再確保 (reallocation)

ベクタの容量とは、そのベクタに将来追加される要素のために確保された空間の量です。これは、ベクタ内の実際の要素数を示す _長さ (length)_ とは混同しないようにしてください。ベクタの長さが容量を超えると、容量は自動的に増やされますが、その要素は再確保されることになります。

たとえば、容量10、長さ0のベクタは、さらに10個の要素分の空きを持つ空のベクタです。10個以下の要素をベクタに push しても容量は変わらず、再確保も発生しません。しかし、ベクタの長さが11に増えると、再確保が発生し、これは遅くなる可能性があります。このため、ベクタがどの程度大きくなると予想されるかを指定するために、可能な限り [`Vec::with_capacity`](#associated-functions) を使うことが推奨されます。

## 保証

その非常に基礎的な性質から、`Vec` はその設計について多くのことを保証しています。これにより、一般的な場合においてオーバーヘッドが可能な限り小さく抑えられ、unsafe なコードから原始的な方法で正しく操作できることが保証されます。これらの保証は、修飾のない `Vec<T>` について述べたものであることに注意してください。（カスタムアロケータのサポートなどのために）追加の型パラメータが加えられ、そのデフォルトが上書きされた場合、挙動が変わることがあります。

最も基本的なこととして、`Vec` は常に (ポインタ、容量、長さ) の3つ組であり、それ以上でもそれ以下でもありません。これらのフィールドの順序は完全に未規定であり、これらを変更するには適切なメソッドを使うべきです。ポインタは決して null になりません。したがってこの型は null ポインタ最適化されています。

しかし、そのポインタが実際に確保されたメモリを指しているとは限りません。特に、[`Vec::new`](#associated-functions)、[`vec![]`](/stable/std/)、[`Vec::with_capacity(0)`](#associated-functions) で容量0の `Vec` を構築した場合、あるいは空の Vec に対して [`shrink_to_fit`](#methods) を呼んだ場合、メモリは確保されません。同様に、`Vec` の中にゼロサイズ型を格納する場合も、そのための空間は確保されません。_この場合、`Vec` が報告する [`capacity`](#methods) が0でないことがある点に注意してください_。`Vec` は `size_of::<T>() * capacity() > 0` であるとき、かつそのときのみ確保を行います。一般に、`Vec` の確保に関する詳細は非常に微妙です。`Vec` を使ってメモリを確保し、それを何か他の目的（unsafe なコードに渡す、あるいは独自のメモリ裏付きコレクションを構築する）に使うつもりなら、`from_raw_parts` を使って `Vec` を復元し、それを drop することで必ずこのメモリを解放するようにしてください。

`Vec` が実際にメモリを確保_している_場合、それが指すメモリはヒープ上にあり（Rust がデフォルトで使うよう設定されているアロケータの定義による）、そのポインタは順に並んだ [`len`](#methods) 個の初期化済みの連続した要素（スライスへ型強制した場合に見えるもの）を指し、その後に `capacity() - len()` 個の、論理的には未初期化の連続した要素が続きます。

容量4で、要素 `'a'` と `'b'` を含むベクタは、次のように図示できます。上の部分は `Vec` 構造体であり、ヒープ上の確保の先頭へのポインタ、長さ、容量を含みます。下の部分はヒープ上の確保、つまり連続したメモリブロックです。

```
        ptr      len  capacity
   +--------+--------+--------+
   | 0x0123 |      2 |      4 |
   +--------+--------+--------+
        |
        v
Heap   +--------+--------+--------+--------+
       |    'a' |    'b' | uninit | uninit |
       +--------+--------+--------+--------+
```

* **uninit** は初期化されていないメモリを表します。[`MaybeUninit`](/stable/std/mem/) を参照してください。
* 注意: ABI は安定しておらず、`Vec` はそのメモリレイアウト（フィールドの順序を含む）について何も保証していません。

`Vec` は、2つの理由から、要素を実際にスタック上に格納する「小さな最適化」を決して行いません。

* そうすると、unsafe なコードが `Vec` を正しく操作することがより難しくなります。`Vec` の内容は、move されただけでも安定したアドレスを持たなくなり、`Vec` が実際にメモリを確保したかどうかを判定することがより難しくなります。
* それは一般的なケースを犠牲にし、すべてのアクセスに追加の分岐を発生させます。

`Vec` は、完全に空になったとしても、決して自動的に自身を縮小しません。これにより、不要な確保や解放が発生しないことが保証されます。`Vec` を空にして、同じ [`len`](#methods) まで再び満たしても、アロケータへの呼び出しは発生しないはずです。使われていないメモリを解放したい場合は、[`shrink_to_fit`](#methods) または [`shrink_to`](#methods) を使ってください。

報告されている容量が十分であれば、[`push`](#methods) と [`insert`](#methods) は決して（再）確保を行いません。`len() == capacity()` であれば、[`push`](#methods) と [`insert`](#methods) は（再）確保を_行います_。つまり、報告される容量は完全に正確であり、信頼できます。望むなら、`Vec` によって確保されたメモリを手動で解放するために使うこともできます。一括挿入を行うメソッドは、必要なくても再確保を行う_ことがあります_。

`Vec` は、満杯になって再確保する際にも、[`reserve`](#methods) が呼ばれた際にも、特定の成長戦略を保証しません。現在の戦略は基本的なもので、非定数の成長率を使うことが望ましいと判明する可能性もあります。どのような戦略が使われるにせよ、もちろん [`push`](#methods) の償却 _O_(1) は保証されます。

プログラマの意図を尊重するため、`vec![e_1, e_2, ..., e_n]`、`vec![x; n]`、[`Vec::with_capacity(n)`](#associated-functions) のいずれも、アロケータに対して正確に `n` 個の要素に必要な、ちょうどそのサイズの確保を要求する `Vec` を生成することが保証されています（たとえば2の累乗に切り上げたサイズなどではありません）。アロケータは要求されたサイズ以上の確保を返しますが、より大きくなることもあります。

[`Vec::capacity`](#methods) メソッドは、要求された容量以上であり、かつ確保された容量以下の値を返すことが保証されています。

[`Vec::shrink_to_fit`](#methods) メソッドは、アロケータが `Vec` に与えた余分な容量を破棄しようとします。`len() == capacity()` であれば、`Vec<T>` は要素を再確保したり move したりせずに [`Box<[T]>`](/stable/std/boxed/) へ、またそこから変換できます。`Vec` は、[`into_boxed_slice`](#methods) のような一般的な変換を実装する際に、この事実を合理的な範囲で最大限活用します。

`Vec` は、そこから取り除かれたデータを特に上書きすることはありませんが、特に保持することもありません。その未初期化のメモリは、好きなように使えるスクラッチ領域です。一般的には、最も効率的な、あるいは実装しやすい方法が選ばれます。セキュリティ上の目的で、削除されたデータが消去されることをあてにしないでください。`Vec` を drop したとしても、そのバッファは単に別の確保によって再利用されるかもしれません。`Vec` のメモリを先にゼロで埋めたとしても、オプティマイザがこれを保持すべき副作用とみなさないため、実際にはそれが起こらないかもしれません。ただし1つだけ、決して破られないケースがあります。それは、unsafe なコードを使って余分な容量に書き込み、その後に長さを増やしてそれに合わせることは、常に妥当である、という点です。

現時点では、`Vec` は要素が drop される順序を保証していません。この順序は過去に変わったことがあり、将来また変わる可能性があります。
